### Anwendung und Fehlerbehandlung

Die CLI-Hilfe des Lockfiles bestätigt die folgenden Optionen. `TEST_REF` bezeichnet jeweils die zuvor verifizierte nicht geheime Projekt-Ref. Aus dem Verzeichnis mit exakt den geprüften Migrationen ausführen. Je Aufruf Ref erneut kontrollieren. [Migrationsverfahren](https://supabase.com/docs/guides/deployment/database-migrations)

```text
supabase migration list --project-ref TEST_REF
supabase db push --project-ref TEST_REF --dry-run --skip-vault
supabase db push --project-ref TEST_REF --skip-vault
supabase migration list --project-ref TEST_REF
```

Vor dem dritten Befehl die vorgeschlagenen Versionen einzeln mit der Tabelle vergleichen. Der Dry-Run listet ausstehende Migrationen und führt deren DDL nicht aus. Kein Seed, keine zusätzlichen Rollen aus einer separaten Datei. Nur eine Person führt Migrationen aus. Danach müssen lokal und remote genau die erwarteten IDs übereinstimmen. Bezug zur SHA, wirksame Rolle, Version, Zeitpunkt, Ergebnis und etwaige Warnungen ohne private Daten festhalten.

Bei Fehler sofort die Freigabe sperren, SQLSTATE, betroffene Anweisung, letzte protokollierte Version und tatsächliche Objekte aufnehmen. Keine blinde Wiederholung oder Journalreparatur. Fehler mit gleicher PG-Version und gleichwertig eingeschränkter Rolle in isolierter Umgebung nachvollziehen. Eine neue Migration eignet sich für einen bereits erreichbaren Ausgangsstand. Scheitert die Erstinstallation in einer älteren Datei, kann eine angehängte Migration sie nicht reparieren. In diesem Fall einen minimalen, explizit reviewten Bootstrap mit getrenntem Nachweis für leere und bestehende Installationen vorlegen. Kein Remote-Reset, keine Änderung an verwalteten Rollen, kein RLS-Abschalten. Für 011A liegt kein reproduzierter Hosted-Fehler und damit keine Migrationskorrektur vor.

## HTTPS, Browser und exakte Rückwege

Dediziertes Vercel-Testprojekt ohne automatische Git-Deployments erstellen. Für einen manuellen Build aus einem sauberen Checkout des kanonischen Repositorys explizit das Preview-Ziel wählen. Vercel liefert generierte Deployment-URLs mit HTTPS. [Vercel CLI](https://vercel.com/docs/cli/deploy) · [Vite und SPA](https://vercel.com/docs/frameworks/frontend/vite) · [Deployment-URLs](https://vercel.com/docs/deployments/generated-urls)

Im Environment **Preview** vor dem Build genau `VITE_SUPABASE_URL` und `VITE_SUPABASE_PUBLISHABLE_KEY` aus dem identifizierten Testprojekt setzen. Der zweite Wert ist dessen veröffentlichbarer Schlüssel. Für jeden neuen Variablenstand neu bauen. Zur Abnahme im Browser eine normale Anfrage der Anwendung bis zum richtigen Supabase-Host nachweisen. Auch geerbte Vercel-Variablen auf ungeeignete VITE-Präfixe prüfen. [Umgebungsvariablen](https://vercel.com/docs/environment-variables)

Erst die eindeutige HTTPS-Deployment-URL als Ursprung **O** feststellen. Unter Supabase Auth die Site URL auf **O** setzen. Exakt **O/auth/callback** und **O/auth/reset-password** als Rückwege zulassen, ohne Wildcards oder lokalen Ursprung. Diese Schreibweise ist ein Schema, keine konfigurierte Adresse. Die beiden vollständigen Werte erst nach dem Deployment oben eintragen. Jeder Wechsel von O braucht neue Einstellungen und einen erneuten Mailtest. Links aus demselben Browserprofil öffnen, das den PKCE-Vorgang begonnen hat. Die App tauscht den Code selbst ein, bereinigt die URL und bindet den Passwortwechsel an den bestätigten Recovery-Vorgang. Einladungen gelangen über das Fragment von `/join` zur App. [Redirects](https://supabase.com/docs/guides/auth/redirect-urls) · [PKCE](https://supabase.com/docs/guides/auth/sessions/pkce-flow)

Bei unpassendem Schutz eine für die Testgruppe zulässige Einstellung nur im isolierten Projekt wählen. Zugangsdaten oder Schutzumgehungsparameter gehören weder in Auth-Links noch ins ZIP. [Deployment Protection](https://vercel.com/docs/deployment-protection)

Nach Prüfung der Deployment-ID `node scripts/hosted/preview.mjs O` mit dem echten Ursprung ausführen. ## Aufbewahrung und Abschluss

Nur synthetische Anzeigenamen, Haushalte und Vorräte erfassen. Vor den späteren freiwilligen Haushaltstests Zweck, sichtbare Daten, Berechtigte, verantwortliche Kontaktperson und konkreten Löschtermin mitteilen. Kamerabilder gehören weder ins Backend noch ins Protokoll. Abbruch des Tests und Löschwunsch bei der Testleitung ermöglichen. Projektregion und tatsächlich beteiligte Dienstleister nennen. Die Region allein belegt keine rechtliche Konformität.

Nach technischer Prüfung Fixture-IDs in einer geschützten, temporären Liste abgleichen. Nur eindeutig zugehörige Haushalte über den Owner-Ablauf `dissolve_household` auflösen. Danach die zugehörigen synthetischen Auth-Konten anhand ihrer ID administrativ entfernen, Restbestände kontrollieren und die temporäre Zuordnung löschen. Bei bestehenden echten Daten keine Sammellöschung. Offene Einladungen widerrufen und Testzugriffe nach Ablauf entziehen. Auth-Konten bis zur gezielten Löschung einplanen. Logs und Sicherungen haben eigene Fristen. Supabase Free nennt regulär einen Tag API-/DB-Logaufbewahrung. Bei Quotenüberschreitung kann das Zeitfenster kürzer ausfallen. Zugriff auf verwaltete Sicherungen hängt vom Tarif ab. Vor einer Änderung an befüllten Testprojekten verfügbaren Wiederherstellungsweg prüfen. Falls ein kontrollierter Export nötig ist, Umfang inklusive Auth-Abhängigkeiten und Rollen sowie Wiederherstellung in separater Umgebung prüfen.
